# GitHub Actions CI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a GitHub Actions CI workflow building and testing the workspace on linux-x86_64, linux-arm64, and macos-arm64 on every push to `main` and every PR — an explicit hard requirement from the original project brief that has never been set up, leaving every commit this project has ever made without any automated regression protection.

**Architecture:** One workflow file (`.github/workflows/ci.yml`) with a build/test matrix job (3 OS/arch legs, native runners for all three — no cross-compilation or emulation) plus two singleton jobs: a workspace-wide fmt check, and an explicit `orchestrator-core`-only job that both runs its tests with zero features and asserts the crate's "zero platform dependencies" invariant via `cargo tree`, turning a check this project has been doing by hand after every change into an enforced CI gate.

**Tech Stack:** GitHub Actions, the existing pinned Rust toolchain (`rust-toolchain.toml`, `1.97.1`), `Swatinem/rust-cache` for dependency caching, `dtolnay/rust-toolchain` for toolchain setup.

**Spec:** None — this plan implements the CI requirement already stated directly in the project's original bootstrap brief ("GitHub Actions CI: build matrix for linux-x86_64, linux-arm64, macos-arm64; run orchestrator-core unit tests on every PR"), plus the specific technical choices confirmed with the human partner (native arm64 runners, not cross-compilation) — see this repo's own commit history/conversation for that confirmation; no separate design doc was written since there was no remaining product ambiguity to resolve.

## Global Constraints

- Native runners for every matrix leg: `ubuntu-latest` (x86_64), `ubuntu-24.04-arm` (arm64, GitHub-hosted native ARM), `macos-latest` (Apple Silicon native, per GitHub's current default). Do not introduce `cross`, QEMU, or any cross-compilation toolchain.
- Pin the toolchain version to match `rust-toolchain.toml` (currently `1.97.1`) rather than hardcoding a duplicate version string in the workflow — read the file at workflow-authoring time and reference it, or use a toolchain-setup action that itself reads `rust-toolchain.toml` (`dtolnay/rust-toolchain` supports a `toolchain-file` mode — verify this at implementation time against that action's current documented inputs, don't assume the exact input name without checking).
- `cargo build --workspace` and `cargo test --workspace` (no explicit `--features` flags) are sufficient per matrix leg to exercise each OS's real backend code paths — `orchestrator-cli`'s and `orchestrator-gui`'s `Cargo.toml` already select the right features per OS via `[target.'cfg(target_os = "...")'.dependencies]` blocks, and Cargo's resolver (this workspace uses `resolver = "2"`) unifies features per-target, so a plain workspace build naturally compiles and tests both the plain (default-features) and OS-featured variants of `orchestrator-hotkey`/`-input`/`-window`/`-core`. Do not add redundant `--features kde,wayland,runner`-style flags to the main matrix job's build/test steps.
- All existing tests in this workspace are confirmed self-contained (no live D-Bus session, no real KWin/ydotoold/portal needed to run any test — verified by grep: every `Connection::session()`/`zbus::Connection` construction appears only in non-test application code, never inside a `#[test]`/`#[tokio::test]` function). `cargo test --workspace` is safe to run unmodified on bare, headless CI runners.
- `cargo clippy --workspace --all-targets -- -D warnings` and `cargo fmt --all --check` must both be part of the required CI gate (matching the project's established practice all session of treating these as non-negotiable before calling anything done).
- Do not add `.deb`/packaging steps, artifact uploads, or a release workflow — out of scope for this plan (a separate future increment per the original project brief's own scoping).
- Do not push to the `origin` remote or open a PR yourself as part of executing this plan — implementers commit locally only. Pushing/PR creation happens once, at the very end, with the human partner's explicit go-ahead (already flagged as a "must ask first" action).

## Task 1: CI workflow

**Files:**
- Create: `.github/workflows/ci.yml`

**Interfaces:** None — this is a leaf artifact with no code-level interfaces to other tasks (there is only one task in this plan).

Read `rust-toolchain.toml` at the repo root yourself before writing the workflow (it currently pins `channel = "1.97.1"`) and use whatever exact toolchain-pinning mechanism you confirm works with `dtolnay/rust-toolchain`'s current documented inputs — check that action's README/documentation directly rather than assuming an input name, since action interfaces change between versions and this plan was written without live internet access to verify the exact current syntax.

- [ ] **Step 1: Write the workflow file**

Create `.github/workflows/ci.yml`:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

env:
  CARGO_TERM_COLOR: always

jobs:
  build-and-test:
    name: build-and-test (${{ matrix.name }})
    strategy:
      fail-fast: false
      matrix:
        include:
          - name: linux-x86_64
            os: ubuntu-latest
          - name: linux-arm64
            os: ubuntu-24.04-arm
          - name: macos-arm64
            os: macos-latest
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4

      - name: Install Rust toolchain
        uses: dtolnay/rust-toolchain@master
        with:
          toolchain: "1.97.1"
          components: clippy, rustfmt

      - uses: Swatinem/rust-cache@v2

      - name: Build workspace
        run: cargo build --workspace --verbose

      - name: Test workspace
        run: cargo test --workspace --verbose

      - name: Clippy
        run: cargo clippy --workspace --all-targets -- -D warnings

  fmt:
    name: fmt
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install Rust toolchain
        uses: dtolnay/rust-toolchain@master
        with:
          toolchain: "1.97.1"
          components: rustfmt

      - uses: Swatinem/rust-cache@v2

      - name: Check formatting
        run: cargo fmt --all --check

  orchestrator-core-zero-deps:
    name: orchestrator-core (zero platform deps)
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install Rust toolchain
        uses: dtolnay/rust-toolchain@master
        with:
          toolchain: "1.97.1"

      - uses: Swatinem/rust-cache@v2

      - name: Test orchestrator-core with default (zero) features
        run: cargo test -p orchestrator-core --verbose

      - name: Assert zero platform dependencies
        run: |
          set -euo pipefail
          TREE="$(cargo tree -p orchestrator-core -e normal)"
          echo "$TREE"
          if echo "$TREE" | grep -qE '\b(tokio|zbus|ashpd|tracing)\b'; then
            echo "::error::orchestrator-core's default dependency tree leaked a platform dependency (tokio/zbus/ashpd/tracing) -- this crate must stay zero-platform-deps by default."
            exit 1
          fi
```

Adjust the `dtolnay/rust-toolchain` `with:` block if your research into that action's current documented inputs shows a cleaner way to point it at `rust-toolchain.toml` directly (e.g. a `toolchain-file: rust-toolchain.toml` input) rather than duplicating the version string `"1.97.1"` in three places in this file — duplicating the exact same literal is acceptable if that's genuinely the simplest reliable option, but check first; do not silently duplicate a value that has a direct-reference alternative without at least trying it.
